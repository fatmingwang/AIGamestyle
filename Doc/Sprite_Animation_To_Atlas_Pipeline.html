Sprite Animation Sequence to Atlas Pipeline

Date: 2026-07-06

Project: Game Style AI / ComfyUI Asset Pipeline

Scope: Generating consistent character animation frames (walk, idle, etc.) with ComfyUI and packing them into a game-ready sprite sheet + atlas

Goal

Turn one character reference image into a set of animation frames (e.g. an 8-frame walk cycle, a 2-4 frame idle loop) that stay visually consistent frame-to-frame, then pack those frames into a single sprite-sheet PNG plus a JSON atlas that a game engine can load directly.

This is a 5-stage pipeline. Stage 2 (the pose skeleton library) is built once and reused for every future character — only Stages 1, 3, 4, 5 repeat per character.

Pipeline Diagram

Stage 1 Stage 2 Stage 3 Stage 4 Stage 5 Character ─┐ Pose skeleton ─┐ IPAdapter + ControlNet Background ─► Pack frames reference │ library │ batch generation ─► removal into atlas image │ (reused ────────────────┘ (one KSampler batch, (spritesheet │ forever) fixed seed, N frames) PNG + JSON) └──────────────────────────────────────────────┘

Stage 1 — Character Reference Generation

Produce one clean, front/side-view illustration of the character in your target art style. This image becomes the "identity anchor" that IPAdapter locks onto for every frame in every animation.

  • Reuse the existing Z-Image-Turbo template (TestData/Text2Image/gsl_starter_1.json via run_text2image.py) to generate this reference from a text prompt, or
  • Supply an existing character illustration directly.

Output: one PNG, e.g. character_ref.png.

Stage 2 — Pose Skeleton Library (build once, reuse forever)

This stage produces the OpenPose-format skeleton images that drive each animation frame's pose. Because ControlNet-openpose conditioning is character-agnostic, this library is built one time and reused for every character skin from then on. There are three ways to build it — pick based on how much control vs. speed you want.

Method A — Use a free pose pack (fastest, zero generation)

Check existing community libraries before generating anything: Civitai's OpenPoses Collection, pose-depot on GitHub, and openposes.com all publish ready-made OpenPose skeleton sets, some including walk cycles. If one matches closely enough, download it and rename the frames to pose_walk_01.png … pose_walk_08.png — Stage 2 is done with no generation step at all.

Method B — Procedural generation script (recommended for repeatability)

A walking gait's joint angles (hip/knee/ankle) follow well-understood sinusoidal curves over the cycle — this is the standard technique behind procedural walk animation in game engines, not something specific to AI. A single script can:

  1. Compute 2D joint positions for N frames from a few numeric parameters (stride length, bounce height, frame count, leg length).
  2. Render them in OpenPose's canonical skeleton-color convention (colored bones on a black background — the exact format ControlNet expects).
  3. Write pose_walk_01.png … pose_walk_08.png directly.

No footage, no manual joint-dragging. Idle uses the same script with near-zero amplitude (just a breathing/sway wobble); run/jump can reuse the same parameter set later. This is the most reusable option — regenerating with different stride/bounce/frame-count parameters takes seconds.

Method C — Extract from a reference video (fallback, most naturalistic)

  1. Install comfyui_controlnet_aux (ComfyUI Manager → search "ControlNet Auxiliary Preprocessors", or git clone into _comfyui/ComfyUI/custom_nodes).
  2. Find or record a short reference clip of the motion (a side-view walk loop, an idle breathing loop, etc.).
  3. Run the DWPose Estimator node (dw_openpose_full) over evenly-spaced frames of that clip.
  4. Save the results as the same numbered sequence as above.

Higher effort (footage sourcing/recording), but captures naturalistic secondary motion that a pure sine-wave model won't — useful if the procedural result looks too mechanical.

Not recommended: text-prompting an image-generation model (Gemini, SDXL, etc.) to directly draw a stick-figure skeleton per frame. Diffusion models routinely produce anatomically broken joints/proportions on skeleton drawings, which defeats the purpose of feeding a precise conditioning image into ControlNet.

Output: a poses/ folder of skeleton PNGs, organized per animation name. This folder is the deliverable of this stage — never regenerate it per character.

Stage 3 — Character-Consistent Frame Batch Generation

This is the core generation graph. It must run on an architecture that ControlNet + IPAdapter actually support — SD1.5, not the Z-Image-Turbo (Lumina2/DiT) checkpoint used for backgrounds. comfyui_ipadapter_plus is already installed but has no weight files yet (see Prerequisites below).

Graph, run once per animation as a single batch:

NodeRole
CheckpointLoaderSimpleLoads the SD1.5 2D/game-art checkpoint
LoadImageLoads character_ref.png from Stage 1
IPAdapterUnifiedLoader + IPAdapterApply/AdvancedLocks the character's identity/style across all frames
Batch image loaderLoads all pose_*.png skeletons for this animation as one IMAGE batch
ControlNetLoader (openpose) + ControlNetApplyDrives each frame's pose from the batch of skeletons
CLIPTextEncode (positive/negative)Style + action description prompt
EmptyLatentImage (batch_size = N)N = number of frames in this animation
KSamplerOne fixed seed for the whole batch — this is what keeps all N frames coherent with each other
VAEDecodeDecodes the batch back to N images

Run this once for "walk" (batch_size 8) and once for "idle" (batch_size 2-4).

Output: N raw frames per animation, e.g. walk_raw_00.png … walk_raw_07.png.

Stage 4 — Background Removal

Feed the decoded batch through the rembg node already installed in this project (comfyui-inspyrenet-rembg or comfyui-rmbg) to get clean alpha-channel frames. No new install required.

Output: walk_00.png … walk_07.png with transparent backgrounds, same canvas size and character-centered framing across all frames (required for a stable pivot point at runtime).

Stage 5 — Pack into Atlas

Extend the existing automation pattern (TestData/Text2Image/run_text2image.py, ComgyUIPythonCommonFunction.py) with a packing script that:

  1. Tiles the frame PNGs into one sprite-sheet PNG (horizontal strip, via Pillow).
  2. Emits a TexturePacker-style JSON atlas (frame name, x/y/w/h, duration) — importable by Unity, Cocos2d, Phaser, PixiJS, LibGDX, and Godot without a proprietary format lock-in.

Example atlas JSON shape:

{
  "frames": {
    "walk_00": { "frame": { "x": 0,   "y": 0, "w": 128, "h": 128 }, "duration": 100 },
    "walk_01": { "frame": { "x": 128, "y": 0, "w": 128, "h": 128 }, "duration": 100 }
  },
  "meta": { "image": "walk_atlas.png", "size": { "w": 1024, "h": 128 } }
}

If the target engine specifically requires Aseprite-format atlases instead, ComfyUI-GameAssetsMaker provides dedicated nodes for that format.

Output: walk_atlas.png + walk_atlas.json, ready to import into the game engine.

Time / Setup Notes

  • Stage 2 is a one-time cost per motion type (walk, idle, run, attack, ...), not per character.
  • Stages 1, 3, 4, 5 repeat per character but are fully scriptable once the workflow JSON and packing script exist.
  • Total one-time download size for Prerequisites: roughly 5-8 GB (SD1.5 checkpoint + ControlNet + IPAdapter + CLIP vision).

Open Decisions Needed

  1. Target game engine — determines whether the Stage 5 atlas should be TexturePacker-style JSON (Unity/Cocos2d/Phaser/PixiJS/LibGDX/Godot) or Aseprite-format.
  2. Character reference source — generate fresh via the existing Z-Image-Turbo template, or supply an existing illustration to use as the IPAdapter anchor.
